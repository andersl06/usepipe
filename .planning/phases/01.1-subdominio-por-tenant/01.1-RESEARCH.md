# Phase 01.1: Subdomínio por tenant no padrão Blip - Research

**Researched:** 2026-09-24
**Domain:** Multi-tenant DNS/TLS wildcard, Traefik, cookie de sessão cross-subdomain, resolução de tenant pelo Host, CORS de origem dinâmica
**Confidence:** MEDIUM — infraestrutura atual bem documentada no repo (HIGH), mas o padrão de subdomínio por tenant é 100% novo (nada no código faz isso hoje); provedor DNS-01 e domínio final têm lacunas reais (ver Open Questions)

## Summary

Hoje o Pipe é multi-tenant **por banco** (uma linha `tenant_id` por tabela + RLS), não **por URL**: todos os clientes compartilham as mesmas quatro origens fixas (`app.`, `gestao.`, `crm.`, `api.usepipe.com.br`), e o tenant sai da sessão (cookie → tabela `sessao` → `tenant_id`), nunca do `Host`. Não existe nenhum middleware, guard ou lógica de resolução de tenant pelo cabeçalho `Host` em nenhum dos três fronts nem na API — este é trabalho 100% novo desta fase, não uma correção de algo que já existe e está errado.

A boa notícia é que a base já está pronta para a mudança em três pontos: (1) o cookie de sessão já é emitido com `Domain=.usepipe.com.br` (ponto na frente) e por isso já atravessa subdomínios — a técnica que a fase pede já está em produção, só falta estendê-la a `*.usepipe.ai`; (2) o tenant já tem `slug` único (`tenant.slug`, `apps/api/src/provisionar.ts`) que serve perfeitamente como label de subdomínio, com validação de formato (mas sem lista de reservados ainda); (3) o `.env.example` já documenta a intenção — variáveis `PIPE_DOMINIO_CONTAS` e `PIPE_PORTA_PUBLICA` existem desde antes desta fase, comentadas com a MESMA descrição do padrão Blip ("cada conta tem o seu subdomínio... quem entra pelo hub cai na sua"), mas **nenhum código lê essas duas variáveis** — são placeholders vazios, puro documento de intenção.

A má notícia é que dois pontos do desenho atual quebram de verdade sob subdomínio por tenant, e são o núcleo do trabalho desta fase: (1) `PIPE_ORIGENS` é uma lista fechada e literal de origens (CORS + validação de `?origem=` no login + `Origin` do WebSocket) — com um subdomínio por cliente essa lista se torna infinita, e o próprio script de deploy (`infra/compose/implantar.sh:130`) hoje **recusa** qualquer curinga em `PIPE_ORIGENS`; a checagem de origem precisa virar padrão (regex de sufixo `.usepipe.ai`), não lista; (2) os links entre apps (Gestão→Desk, e a URL de convite) são **assados em build time** como uma única constante global (`VITE_PIPE_DESK_URL`, `PIPE_URL_APP`) via `infra/construir-imagens.sh` — isso não tem como funcionar quando cada tenant tem seu próprio subdomínio, porque a URL do Desk do cliente A é diferente da URL do Desk do cliente B, e a imagem Docker é a mesma para todos. Esses links precisam passar a ser calculados em runtime a partir do slug do tenant logado (que já vem em `GET /v1/eu` → `tenant.slug`).

No lado de infraestrutura, o Traefik de produção (`infra/compose/docker-compose.prod.yml`) usa hoje desafio **HTTP-01** (`--certificatesresolvers.le.acme.httpchallenge.entrypoint=web`), que **não emite certificado wildcard** — é preciso migrar para DNS-01. O dono usa DNS na Hostinger; o `lego` (biblioteca de ACME que o Traefik usa por dentro) tem provider `hostinger` desde uma versão relativamente recente (variável `HOSTINGER_API_TOKEN`), mas a versão pinada no compose (`traefik:v3.3`) é de bem antes disso — precisa confirmar se o lego embutido nela já inclui o provider Hostinger, ou trocar para uma tag mais nova (`v3.7.x`, atual em set/2026). Cloudflare é a alternativa madura de sempre (o projeto já tem provider Terraform Cloudflare para DNS de outro módulo) e é fallback direto se o Hostinger não estiver disponível na versão do Traefik ou se a zona for delegada para lá.

**Primary recommendation:** Introduzir um middleware de resolução de tenant pelo `Host` (novo, na API e/ou nos fronts) que extrai o slug do subdomínio e valida contra `tenant.slug`; trocar a checagem de origem de lista fechada para regex de sufixo de domínio (`^https://[a-z0-9-]+\.usepipe\.ai$` mais os hosts fixos que sobrarem — `api.`, `www.`); mover o Traefik para DNS-01 com o provider da Hostinger (ou Cloudflare como fallback) e emitir um certificado wildcard `*.usepipe.ai` + `*.desk.usepipe.ai` (dois níveis de wildcard, porque `<tenant>.desk.usepipe.ai` é um terceiro nível); trocar os links assados em build time (Gestão→Desk, convite) por URLs calculadas em runtime a partir do slug do tenant da sessão atual; e criar lista de subdomínios reservados (`www`, `api`, `app`, `admin`, `desk`, `metricas`, `arquivos`, etc.) que nenhum slug de tenant pode colidir.

### Pattern 1: Tenant resolvido pelo Host, mas AUTORIZADO pela sessão (defesa em profundidade)

**What:** O `Host` da requisição nunca é a única fonte de verdade sobre "quem é o tenant" — ele é um sinal a mais que precisa CASAR com o `tenant_id` já presente na sessão (cookie). Se alguém troca a URL para o subdomínio de outro cliente mas mantém o cookie da própria sessão, a requisição é recusada (não silenciosamente redirecionada para o tenant errado).

**When to use:** Toda rota autenticada da API, e a tela de login/pré-sessão (onde ainda não há cookie — aí o Host decide para qual tenant mandar o desafio OAuth).

**Example:**
```typescript
// Padrão a seguir (não existe ainda no repo) — mesma forma de
// apps/api/src/controladores/entrar.ts (guarda de erro nunca 500 para quem
// está entrando) e do guard ComSessao() em apps/api/src/sessao.ts
export function slugDoHost(host: string | undefined, dominioBase: string): string | null {
  if (!host) return null;
  const semPorta = host.split(':')[0]!.toLowerCase();
  // <slug>.desk.<base>  OU  <slug>.<base> — dois padrões válidos (D-42, Phase 01.1)
  const sufixoDesk = `.desk.${dominioBase}`;
  const sufixoApp = `.${dominioBase}`;
  if (semPorta.endsWith(sufixoDesk)) return semPorta.slice(0, -sufixoDesk.length) || null;
  if (semPorta.endsWith(sufixoApp) && semPorta !== `api${sufixoApp}` && semPorta !== `www${sufixoApp}`) {
    return semPorta.slice(0, -sufixoApp.length) || null;
  }
  return null;
}
```

### Pattern 2: Origem permitida por regex de sufixo, não lista literal

**What:** Trocar `PIPE_ORIGENS` de "lista fechada e enumerada" para "um padrão de sufixo de domínio + uma pequena lista de hosts fixos que sobram" (ex.: `api.` não precisa estar na lista de origens de CORS porque nunca é chamador, só destino).

**When to use:** `enableCors` em `apps/api/src/servidor.ts:50-60`, `origemPermitida`/`origensPermitidas` em `packages/autenticacao/src/sessao.ts`, e a checagem de `Origin` do WebSocket em `apps/api/src/eventos-ws.ts:77-80`.

**Example:**
```typescript
// Fonte: packages/autenticacao/src/sessao.ts:104-121 (código atual, para comparação)
// hoje: lista literal vinda de PIPE_ORIGENS, split por vírgula
export function origensPermitidas(env: NodeJS.ProcessEnv = process.env): string[] {
  const cru = env['PIPE_ORIGENS'] ?? '';
  return cru.split(',').map((o) => o.trim().replace(/\/$/, '')).filter(Boolean);
}
// proposta: manter a função (compat com testes existentes), acrescentar uma
// segunda que aceita por regex de sufixo — os dois modos convivem durante a
// migração, e o padrão de subdomínio nunca aceita `*` puro (exigência do
// próprio infra/compose/implantar.sh:130, que recusa curinga literal — o
// regex de sufixo não é a mesma coisa que a string "*" no env)
```

### Anti-Patterns to Avoid

- **Assar a URL do Desk/API por tenant em build time:** é exatamente o padrão atual (`VITE_PIPE_DESK_URL`, `infra/construir-imagens.sh:35-47`) e não escala para "uma URL por cliente" — a imagem Docker é UMA só, compartilhada por todos os tenants. Trocar para cálculo em runtime a partir do `Host` atual e do `tenant.slug` da sessão.
- **Curinga literal em `PIPE_ORIGENS`:** o script de deploy já recusa isso de propósito (`infra/compose/implantar.sh:130-132`) — não tentar contornar com `*`; o padrão certo é regex de sufixo dentro do código, não no valor do env.
- **`SameSite=None` para "resolver" cookie cross-subdomínio:** o comentário do próprio código já explica por que isso é pior (`packages/autenticacao/src/sessao.ts:61-64`) — `Domain=.usepipe.ai` já resolve sem abrir a porta que `None` abriria.
- **Confundir "domínio verificado" (SSO por domínio de e-mail, `dominio_tenant`) com "subdomínio de acesso":** são dois sistemas diferentes que já coexistem no código (`apps/api/src/dominio/dominios.ts` é sobre `@empresa.com.br` no e-mail decidir o tenant no login; esta fase é sobre `acme.usepipe.ai` na URL). Não misturar os dois na hora de nomear variáveis/tabelas novas.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Emissão/renovação de certificado wildcard | Script próprio de ACME/DNS-01 | `certificatesresolvers.*.acme.dnschallenge` do Traefik (lego embutido) | Já é o mecanismo em produção para HTTP-01; trocar de desafio é configuração, renovação automática já existe |
| Parsing de subdomínio | Regex ad-hoc espalhada em cada front | Uma função só (`slugDoHost`, ou equivalente) em `packages/autenticacao` ou pacote novo pequeno, importada pela API e (se necessário) pelos fronts | Evita duas implementações divergentes de "o que é um slug válido" — o projeto já tem essa disciplina para `origemPermitida` |
| Validação de nome de subdomínio | Regex nova para "nome de host válido" | Reaproveitar `SLUG_ACEITAVEL` de `apps/api/src/provisionar.ts:66` (minúsculas, números, hífen no meio) — já é compatível com regra de DNS label | O slug já É o subdomínio; não inventar uma segunda regra |

**Key insight:** Quase todo o mecanismo necessário (cookie cross-subdomínio, slug único, checagem de origem, guarda de sessão) já existe no projeto num formato "fixo" (4 hosts conhecidos). O trabalho real é generalizar esses mecanismos para "N hosts, um por tenant, com o mesmo padrão" — não é construir do zero.

## Common Pitfalls

### Pitfall 1: TTL do registro DNS-01 travando a emissão do wildcard
**What goes wrong:** Ao pedir certificado para `usepipe.ai` (apex) e `*.usepipe.ai` juntos, o registro TXT do desafio DNS-01 é o MESMO para os dois nomes — se o TTL do provedor DNS for alto, o segundo desafio expira esperando o TXT antigo cair de cache.
**Why it happens:** Comportamento documentado do próprio Let's Encrypt/lego, não bug do Traefik. [CITED: doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/]
**How to avoid:** Pedir o wildcard e o apex em resolvers/domains separados, ou baixar o TTL do registro TXT no provedor DNS antes da primeira emissão.
**Warning signs:** Log do Traefik com timeout no desafio DNS-01, especialmente na primeira tentativa após configurar.

### Pitfall 2: Cookie de sessão emitido antes do Host ser confiável
**What goes wrong:** Se o middleware de resolução de tenant por Host rodar DEPOIS do parser de cookie/sessão do NestJS, uma sessão válida de um tenant pode ser aceita num Host de outro tenant sem nunca ser confrontada.
**Why it happens:** Ordem de middleware importa; o guard de sessão (`ComSessao()`) hoje não sabe nada sobre Host porque Host nunca importou antes desta fase.
**How to avoid:** O confronto Host↔tenant precisa acontecer no MESMO guard (ou logo antes) que resolve a sessão, não como checagem opcional depois.
**Warning signs:** Testar manualmente: logar no subdomínio do tenant A, trocar a barra de endereço para o subdomínio do tenant B mantendo o cookie — se a tela carrega dados do tenant A sob o Host de B, o guard está incompleto.

### Pitfall 3: `PIPE_ORIGENS` continuar sendo lida como lista literal em algum lugar esquecido
**What goes wrong:** A função `origensPermitidas()` é chamada em pelo menos três lugares (`servidor.ts` para CORS, `entrar.ts` para validar `?origem=`, `eventos-ws.ts` para o `Origin` do WebSocket). Trocar a lógica só num lugar deixa os outros dois ainda recusando qualquer subdomínio novo.
**Why it happens:** É a mesma função reaproveitada de propósito hoje (boa prática atual) — a migração precisa preservar esse reaproveitamento, não convém duplicar em três formatos diferentes.
**How to avoid:** Fazer a troca dentro de `packages/autenticacao/src/sessao.ts` (o único lugar onde a lógica mora) e deixar os três chamadores intocados.
**Warning signs:** Login funciona mas WebSocket cai com 403, ou vice-versa — sintoma de que só um dos três chamadores foi migrado.

### Pitfall 4: `VITE_PIPE_DESK_URL`/`VITE_URL_API` continuarem assados por build, front "funcionando" só em produção por acidente
**What goes wrong:** Como a imagem é construída com uma URL fixa (`infra/construir-imagens.sh:43-47`), é fácil "resolver" o problema trocando o valor default para um padrão com placeholder (`https://{slug}.desk.usepipe.ai`) sem trocar ONDE o valor é lido — ele continuaria sendo lido em build time, nunca em runtime, e todo tenant receberia o link do PRIMEIRO tenant buildado.
**Why it happens:** `NEXT_PUBLIC_*`/`VITE_*` são conhecidamente assados no bundle (o próprio comentário do script já avisa isso para outro motivo, `infra/construir-imagens.sh:35-39`) — é fácil esquecer que a mesma regra vale aqui.
**How to avoid:** O link cross-app tem que ser montado em código JS que roda no navegador, usando `window.location.hostname` (para saber se já está em `desk.` ou não) + o `tenant.slug` que vem de `GET /v1/eu` — nunca uma env var assada.
**Warning signs:** Todos os clientes, ao clicar de Gestão para Desk, caírem no MESMO subdomínio (o do primeiro build).

### Pitfall 5: Subdomínio de tenant colidindo com host reservado
**What goes wrong:** Um cliente escolhe (ou tenta escolher via autosserviço) o slug `api`, `www`, `admin` ou `desk` — e o Traefik passa a rotear tráfego de um "tenant" para o serviço interno errado, ou o próprio padrão `<slug>.desk.usepipe.ai` colide com `desk` como nome de tenant em `<slug>.usepipe.ai`.
**Why it happens:** Hoje não existe lista de reservados — `SLUG_ACEITAVEL` (`apps/api/src/provisionar.ts:66`) só valida FORMATO, nunca colisão com host de sistema.
**How to avoid:** Lista fixa de reservados (`www`, `api`, `app`, `admin`, `desk`, `metricas`, `arquivos`, `mail`, `status`) checada em `provisionarCliente` e em qualquer fluxo futuro de autosserviço que deixe o cliente escolher o próprio slug.
**Warning signs:** Nenhum ainda — é prevenção, não sintoma observado.

## Open Questions

1. **Domínio final: `usepipe.ai` ou `usepipe.com.br`?**
   - O que sabemos: `.env.example` já teoriza `usepipe.ai`; produção hoje roda em `usepipe.com.br`; o roadmap da fase 01.1 escreve `usepipe.ai` mas também diz "ou similar, a definir".
   - O que é incerto: se a migração de domínio (registrar `.ai`, trocar DNS, reemitir credencial OAuth do Google com nova URL de retorno) faz parte desta fase ou é decisão separada.
   - Recomendação: perguntar direto ao dono antes do plano — é a decisão que mais barateia (ou encarece) todo o resto, porque toda regex/env/Terraform desta fase referencia esse valor.

2. **Provider de DNS-01: Hostinger direto ou migrar a zona para Cloudflare?**
   - O que sabemos: dono usa Hostinger para DNS hoje; lego tem provider Hostinger; versão exata embutida no Traefik pinado é incerta (A1); o repo já tem Terraform Cloudflare pronto para outro módulo.
   - O que é incerto: se vale a pena testar o provider Hostinger primeiro (mais simples, sem trocar nameserver) ou já migrar para Cloudflare (mais maduro, sem risco de versão).
   - Recomendação: primeiro plano deve incluir uma tarefa de verificação rápida (`traefik version` na imagem pinada + checar se `hostinger` está no binário, ou simplesmente tentar subir com `HOSTINGER_API_TOKEN` num ambiente de teste) antes de comprometer a decisão.

3. **Path exato do Gestão/Portal: `<tenant>.usepipe.ai/application` tem basename fixo, ou é só a rota inicial dentro de um app sem prefixo?**
   - O que sabemos: D-42 (Phase 1, já travado) já nomeou o módulo principal do Portal como `application`; hoje o roteador da Gestão não usa `basename` nenhum.
   - O que é incerto: se `/application` é o NOME da rota raiz dentro do app (equivalente a hoje ter `/portal`, `/fluxo/:id` etc. na raiz) ou um prefixo de `basename` que precede todas as rotas existentes.
   - Recomendação: decisão de nomenclatura/roteamento, não de infraestrutura — provavelmente já é escopo do discuss-phase desta fase, não desta pesquisa; registrar como pergunta ao dono no portão de decisões.

4. **Usuário em dois tenants ao mesmo tempo — confirmar que a restrição atual (uma identidade Google = um tenant, `EntradaRecusada('outro_tenant', ...)`) continua valendo?**
   - O que sabemos: o código HOJE recusa explicitamente ligar a mesma conta Google a dois tenants (`packages/autenticacao/src/entrada.ts`, erro `outro_tenant`).
   - O que é incerto: se a introdução de subdomínio por tenant motiva revisitar essa restrição (ex.: um consultor que atende dois clientes Pipe com o mesmo e-mail corporativo).
   - Recomendação: se a restrição continuar valendo (cenário mais provável, é decisão de produto separada), a resolução de tenant por Host fica mais simples — o Host nunca precisa "escolher entre dois tenants possíveis" para a mesma sessão. Confirmar com o dono que não é isto que a fase pretende mudar.

### Known Threat Patterns for este domínio

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Subdomain takeover (DNS wildcard apontando para algo que já não existe) | Spoofing | Nunca deixar registro wildcard "solto" sem serviço atrás; monitorar que o wildcard sempre resolve para o Traefik ativo |
| Cross-tenant session confusion (cookie de A usado no Host de B) | Tampering / Elevation of Privilege | Pattern 1 (confronto Host↔tenant no guard de sessão) — é a mitigação central desta fase |
| Open redirect via `?origem=`/`?destino=` para subdomínio arbitrário | Tampering | Já existe defesa (`origemPermitida`, `destinoAbsoluto` só aceita caminho interno) — ao trocar lista fixa por regex, a regex PRECISA continuar recusando qualquer coisa fora do padrão `*.usepipe.ai`, nunca aceitar qualquer host |
| Cross-site WebSocket hijacking via `Origin` fora do padrão | Spoofing | Já existe defesa (`eventos-ws.ts:77-80`); ao trocar para regex, aplicar a MESMA função nova de `origemPermitida`, não duplicar lógica |
| Subdomínio reservado sequestrado por slug de tenant malicioso | Spoofing / Elevation of Privilege | Lista de reservados (Pitfall 5) checada em `provisionarCliente` e em qualquer autosserviço futuro |
