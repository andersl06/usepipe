<objective>
P06 part 1 of 2 (API): Pipe Chat, an embeddable web chat like Blip's web chat. Minimal viable embed per CONTEXT.md: script snippet + channel config + messaging round trip. This plan builds the server side; plan 12 builds the embed bundle and the config page.

Commit note: P06 is delivered in two commits (`feat(03.3-P06): pipe chat api` here, `feat(03.3-P06): pipe chat embed and config page` in plan 12) because it spans two subsystems that do not fit one plan's context budget; both carry the P06 tag. This is the only point split across two commits.

Design (no new dependency, no schema change):
- Channel: `canal` row with tipo 'widget' (already allowed by TYPES_CHANNEL / CHECK). `config` jsonb holds `widgetKey` (public, 32 hex chars from randomBytes(16)), `widgetSecret` (64 hex chars from randomBytes(32), encrypted at rest by adding it to the secret field list in packages/db/src/secret.ts, never returned by any endpoint), `allowedOrigins: string[]` (exact `scheme://host[:port]`), `greeting: string`.
- Key lookup: `databaseOwner()` select from canal where tipo = 'widget' and ativo and config->>'widgetKey' = key limit 1, same no-tenant-yet pattern as `redirecionarClique` in rastreador-de-cliques.ts. Mark with a `ponytail:` comment that this is an unindexed jsonb scan over widget channels and an expression index needs a reserved migration number when widget channels grow.
- Visitor: visitorId = randomUUID(); token = HMAC-SHA256(widgetSecret, visitorId) hex, verified with timingSafeEqual. Stateless, no table.
- Inbound: build a WhatsApp-Cloud-shaped payload (`object: 'whatsapp_business_account'`, one entry, one change with `value.contacts[{ wa_id: visitorId, profile: { name } }]` and `value.messages[{ from: visitorId, id: randomUUID(), timestamp: seconds, type: 'text', text: { body } }]`) and call `enqueueInbound(channelId, payload)`; the shared `processarPayload` -> `extractValues` path then creates contact, contato_identidade (canal_tipo 'widget', identificador visitorId), conversation/execution and runs the linked flow, exactly like the Instagram/Messenger adapters reuse it. inbound.ts is NOT edited.
- Outbound: GET messages reads `mensagem` rows of this visitor's contact on this channel (join conversa/execucao_fluxo -> inbox.canal_id = channel, contact via contato_identidade canal_tipo 'widget' identificador visitorId) newer than `since`, max 50, returning { id, direction, text, createdAt } with text = conteudo text only. Delivery worker short-circuits widget rows to `enviada`.
- CORS: global credentialed CORS stays for everything else; for paths starting with `/v1/widget/` the delegate returns `{ origin: true, credentials: false, methods: ['GET','POST','OPTIONS'], allowedHeaders: ['content-type'], maxAge: 600 }`; the controller enforces the per-channel Origin allow-list server-side (403), so reflecting the origin at CORS level grants nothing without the allow-list.

Output: domain + public controller + management controller + CORS delegate + shared rate limiter + worker short-circuit + tests + FINDINGS ## P06 (API part).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party website (any origin) -> /v1/widget/:key/* | unauthenticated public surface |
| widget channel key -> tenant | the only way a tenant is chosen on this surface |
| visitor A -> visitor B | visitors of the same channel must not read each other |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03.3-11-01 | Spoofing | tenant selection | mitigate | tenant derived only from resolveWidgetChannel(key) via databaseOwner lookup; request body never carries tenant/channel ids |
| T-03.3-11-02 | Information disclosure | GET messages of another visitor | mitigate | HMAC token per visitorId with per-channel widgetSecret, timingSafeEqual; wrong token -> 404; test |
| T-03.3-11-03 | Denial of service | public endpoints | mitigate | withinRateLimit per key+IP (30/min, 429), text max 2000 chars, GET limit 50 rows |
| T-03.3-11-04 | Elevation of privilege | CORS on widget paths | mitigate | credentials: false on /v1/widget/* only; endpoints never read the session cookie; server-side Origin allow-list -> 403 |
| T-03.3-11-05 | Tampering (stored XSS) | visitor text | mitigate | stored verbatim, returned as JSON string; renderers (widget, Desk, management) use text nodes; test with HTML payload |
| T-03.3-11-06 | Information disclosure | widgetSecret | mitigate | encrypted at rest via secret.ts list; grep gate: no controller serializes it |
| T-03.3-11-07 | Spoofing | Origin header forged by non-browser clients | accept | Origin allow-list protects against browser embedding only (same model as Blip's public app key); rate limit + token bound the abuse |
| T-03.3-11-SC | Tampering | npm installs | mitigate | none performed; Blip widget packages explicitly forbidden |
</threat_model>
