## Summary

Most of what the owner asks for is NOT greenfield: the org switcher, team page, flow log screen, 90-day limits, message-template page, contact identity and router-aware contact list all already exist in code. The work is (a) reproducing why they look broken to the owner, (b) closing gaps against what Blip really does, and (c) two genuinely new builds (Pipe Chat widget, point 6; ticket-grouped history with retention note, point 9). Several earlier "Blip parity" statements in code comments are inaccurate versus the captures (see per-point tables), so the findings doc per point is mandatory, not ceremony.

The biggest research risk: `referencias-blip` captures are mostly EMPTY-STATE snapshots (message-template list, users list, log list had no rows). Anything about row-level data (message-template columns, contact label format `@wa.ms`, ticket info on history rows) cannot be proven from the repo and needs live Blip access or an explicit owner decision. The repo contains no Blip credentials that I could find; treat live confirmation as an owner-supplied input (checkpoint), otherwise put it on the deferred list as CONTEXT.md prescribes.

Real defects found by reading code (candidates, each needs a failing test first): `input-expiration-job.ts` bails out for router service flows (`f.canal_id` is null); `loadChannelOfFlow` (templates) ignores router extra channels; `management-analytics.ts:64` channel label uses only `fluxo.canal_id`; analytics dashboard does not aggregate router services; contact detail picks an arbitrary identity per channel type and has no 90-day cutoff; log page toggle is local-only and Blip-incompatible extra filters were invented.

**Primary recommendation:** Slice into one plan per point (13 plans + 1 findings/verification plan), each starting with a "findings + failing test" task. Do not add any npm dependency. Treat live-Blip confirmation (points 7, 8 row data, 9, 13) as an owner checkpoint with a safe default (implement only what captures prove).

## Common Pitfalls

### Pitfall 1: Treating empty-state captures as full specs
**What goes wrong:** Inventing columns/fields (message-template, history rows, users rows) and calling it "identical to Blip".
**How to avoid:** Findings doc lists PROVEN vs UNPROVEN per element; unproven -> deferred/owner checkpoint.
**Warning signs:** Code comments saying "as in the source" with no capture path.

### Pitfall 2: Router vs flow semantics
**What goes wrong:** Reading `fluxo.canal_id` directly; routers use `roteador_canal` and services have no channel.
**How to avoid:** Always `linkedChannelIdsOfFlow`; resolve a conversation's channel through `inbox.canal_id`.
**Warning signs:** Empty lists on router service pages; null `channelId` in jobs.

### Pitfall 3: Global CSS collisions
**What goes wrong:** New classes reuse `bl-/cf-/ct-` (shared) or a prefix defined elsewhere.
**How to avoid:** grep before adding; tests for prefix uniqueness.

### Pitfall 4: Dirty working tree and parallel branches
Uncommitted modifications exist in `contacts/detalhe/detalhe.tsx`, `editar.tsx`, `settings/api/gravar.ts`, `apps/site/index.html`, `.planning/ROADMAP.md`, `STATE.md`. Branch `codex/fases-1-e-1.1` is checked out in a worktree (`+`). One atomic commit per point means staging only intended files (`git add <paths>`, never `-A`).

### Pitfall 5: Windows/CRLF and Windows shell
Git warns LF->CRLF on touched files; do not reformat whole files. Local API must start with root `.env` loaded (memory `local-dev-startup`); ports 3010 (API) and 3110 (Vite) are currently listening.

### Pitfall 6: Public widget endpoint (P6)
Tenant derived from client input, unbounded message size, reflected HTML, no rate limit, permissive CORS `*` with credentials. See Security Domain.

## Security Domain

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (P2, P6) | existing session cookie + `openSessionAt`; widget uses channel key, not user session |
| V3 Session Management | yes (P2) | new cookie on exchange, cache clear client-side (exists) |
| V4 Access Control | yes (P2, P3, P10) | membership by e-mail, RLS `tenant_isolado` policies, `requirePermission`; 404 not 403 for foreign tenant |
| V5 Input Validation | yes (P6, P8, P13) | validate query params (`DIA` regex, enum includes), body size limits, E.164 validation (exists) |
| V6 Cryptography | yes (P6) | random visitor/channel keys via `node:crypto` `randomUUID`/`randomBytes`; never hand-roll |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-tenant/cross-router data leak (P10) | Information disclosure | RLS + channel-scoped queries via `linkedChannelIdsOfFlow`; isolation test |
| Org enumeration on switch (P2) | Information disclosure | return 404 for non-member (exists) |
| Public widget abuse (P6) | DoS / Spoofing | per-key rate limit, Origin allow-list, size caps |
| Stored XSS via widget/log content (P6, P8) | Tampering | render as React text; `<pre>` text only; never `dangerouslySetInnerHTML` |
| SQL injection in log search (P8) | Tampering | parameterized `ilike ${...}` (exists); escape `%`/`_` in user term if exact matching expected |
| Privilege escalation on team edit (P3) | Elevation | `EDIT_FLOW` permission + last-admin guard (check `team-of-flow.ts`) |
