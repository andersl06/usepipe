# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Natureza desta fase (leia antes de aplicar o contrato):** esta não é uma fase de UI greenfield. D-01/D-02 (`02-CONTEXT.md`) exigem que o catálogo de conteúdo/ação, o schema de pesquisa de satisfação e o desenho exato de cada tela novo do Builder só sejam fixados **depois** de uma investigação da referência (Blip ao vivo → snapshot congelado e datado). Este UI-SPEC fixa o que já é decisão travada (D-30..D-33: paridade visual, tema escuro fixo, mecanismo de token azul→verde, proibição de ícone/imagem da Blip) e o mecanismo de contrato (nomenclatura de token, escala existente, papéis de cor). Não fixa medidas específicas de telas ainda não capturadas (painel de Teste, exportar versão antiga, pesquisa de satisfação) — essas herdam este mecanismo quando o inventário congelado (D-02) e o portão do dono (D-04) estiverem prontos. Qualquer plano/executor que precise de um valor não listado aqui usa a referência capturada (`referencias-blip/builder/`) como fonte, nunca inventa.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — projeto usa sistema de token próprio (não shadcn/Tailwind); ver justificativa abaixo |
| Preset | not applicable |
| Component library | none (componentes próprios em `packages/ui`) |
| Icon library | `packages/ui/src/icones.tsx` (ícones desenhados pelo Pipe; **nunca** ícone/imagem/som da Blip — regra permanente, D-33) |
| Font | `--p-fonte`: `'IBM Plex Sans', -apple-system, 'Segoe UI', Helvetica, Arial, sans-serif`; monoespaçada `--p-fonte-mono`: `'IBM Plex Mono', ui-monospace, Menlo, Consolas, monospace` (só número tabular e rótulo de seção, nunca nome/fila/campo) |

**Por que "none" e não shadcn:** o repositório já tem um sistema de design maduro e documentado (`packages/ui/src/estilos/tokens.css`, `tema.ts`, `docs/specs/2026-09-05-design-system.md`), medido diretamente do bundle da Blip e com regra explícita do dono: nenhum código/CSS/ícone da Blip entra no repositório, e o sistema existente é a fonte de verdade (não inventar um novo). Não há `components.json` nem `tailwind.config.*` no repositório — confirmado por varredura nesta sessão. Introduzir shadcn agora duplicaria a arquitetura de tema já construída (papel constante → valor por tema, `--p-*`) e contradiria a convenção do projeto. O Builder usa CSS próprio (`editor.css`, `painel-bloco.css`) com classes `bl-*`, hoje com hex solto medido do DOM da Blip (ex.: `#393939`, `#4a5d23`) — o trabalho de D-32 é migrar esse hex solto para os tokens semânticos abaixo, não trocar de sistema.

## Spacing Scale

O projeto já declara sua própria escala em `packages/ui/src/estilos/tokens.css` (base 4px, medida na Blip) — reutilizada aqui em vez da escala genérica do template, por instrução explícita de não inventar um novo sistema.

| Token | Value | Usage |
|-------|-------|-------|
| `--p-e-1` | 4px | Gap entre ícone e texto, padding interno mínimo |
| `--p-e-2` | 8px | `--p-celula-y`; espaçamento compacto entre controles |
| `--p-e-3` | 12px | `--p-celula-x`; espaçamento padrão de célula/campo |
| `--p-e-4` | 16px | Espaçamento padrão entre elementos de painel |
| `--p-e-5` | 20px | Espaçamento de seção dentro do painel lateral |
| `--p-e-6` | 24px | Padding de seção/cartão |
| `--p-e-8` | 32px | Espaçamento entre blocos maiores de layout |
| `--p-e-10` | 40px | Espaçamento de topo de página/quebra maior |

**Exceções específicas do Builder (medidas do DOM real da Blip, `editor.css` cabeçalho, não inventadas):**

| Medida | Valor | Onde |
|--------|-------|------|
| Largura do nó (`.bl-no`) | 175px | Canvas |
| Padding interno do nó | 28px | Canvas — não é múltiplo da escala de 4 porque é medição direta do DOM da Blip, preservada por paridade (D-30) |
| Raio do nó / cartão | 8px | Canvas, painéis |
| Anel de seleção/hover | 4px (`box-shadow: 0 0 0 4px`) | Canvas — vira token `--p-builder-marca-anel` (ver Color) |
| Painel lateral do bloco | 360px | `painel.tsx`/`painel-bloco.css` |
| Ponto de saída da conexão | 1em, centrado na borda inferior | Canvas |

Qualquer medida de tela ainda não capturada (painel de Teste, painel de Filas embutido, exportar versão antiga) segue a mesma regra: medir a referência (`referencias-blip/builder/`) quando o snapshot D-02 cobrir aquela tela; até lá, usar a escala `--p-e-*` acima como piso e não inventar espaçamento fora dela.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`--p-t-md`) | 400 (`--p-peso-normal`) | 1.5 (`--p-altura-linha`) |
| Label | 12px (`--p-t-sm`) | 600 (`--p-rotulo-peso`), caixa alta, `letter-spacing: 0.06em` (`--p-rotulo-espaco`) | 1.2 (`--p-altura-linha-curta`) |
| Heading (painel/aba) | 16px (`--p-t-lg`) | 500 (`--p-peso-medio`) | 1.2 |
| Display (título de página) | 20px (`--p-t-titulo`) | 600 (`--p-peso-forte`) | 1.2 |

4 tamanhos confirmados para esta fase: 12 (Label), 14 (Body), 16 (Heading), 20 (Display). `--p-t-numero` (28px, monoespaçada tabular) existe na régua do produto mas não tem uso confirmado nesta fase — a menção anterior a "painel de Teste, se vier a existir" era especulativa; esse tamanho só volta a este contrato quando D-14 confirmar que a tela usa número de destaque.

**Os três pesos (400/500/600) não são uma declaração nova desta fase — são a convenção já aprovada em todo o produto**, documentada em `docs/specs/2026-09-05-design-system.md` §3.6 "Régua tipográfica" (tabela "Pesos — 400 / 500 / 600") e implementada em `packages/ui/src/estilos/tokens.css:154-156` (`--p-peso-normal`, `--p-peso-medio`, `--p-peso-forte`). Este UI-SPEC reutiliza essa régua existente em vez de inventar uma nova para o Builder.

**Exceção documentada — título do nó no canvas:** 14px/400 (`--p-t-md`/`--p-peso-normal`), passando a 700 quando o bloco está selecionado. 700 não existe na régua de três pesos (`--p-peso-normal`/`--p-peso-medio`/`--p-peso-forte`) do resto do produto — é medição direta do DOM da Blip preservada por paridade visual (D-30) e já documentada no cabeçalho de `editor.css`. Não generalizar esse quarto peso para fora do título do nó.

## Color

O Builder é **sempre escuro**, independente do alternador de tema do resto do produto (D-31 — "o builder não é claro, é tudo escuro"). O contêiner raiz do Builder deve forçar o escopo escuro (mecanismo já existente em `tokens.css`: seletor `:root[data-tema='escuro']`), não seguir `prefers-color-scheme` nem a preferência salva do usuário para o resto do app.

**Âncora visual do canvas:** com um bloco selecionado, o anel de marca do nó (`--p-builder-marca-anel`, `box-shadow: 0 0 0 4px`) é o ponto focal da tela — todo o resto (demais nós, painel lateral, fundo) fica em tokens de superfície neutros para não competir com ele. No estado vazio (fluxo novo, sem blocos), o foco passa para o texto do empty state ("Comece pelo primeiro bloco" — ver Copywriting), que ocupa o centro do canvas.

| Role | Value (tema escuro, tokens existentes) | Usage |
|------|-------|-------|
| Dominant (60%) | `--p-superficie-1` escuro `#12140e` | Fundo do canvas |
| Secondary (30%) | `--p-superficie-0` escuro `#1a1d15` (nó, cartão) / `--p-superficie-2` escuro `#232619` (painel lateral, recesso) | Nós, painel lateral, cabeçalho |
| Accent (10%) | `--p-marca` escuro `#a3b76a` como semente — granularizado abaixo | Ver lista fechada de elementos |
| Destructive | `--p-erro-conteudo` escuro `#e4816d` sobre `--p-erro-fundo` escuro `#3a211b` | Excluir bloco, excluir ligação, descartar rascunho — sempre com confirmação (ver Copywriting) |

**Accent reserved for (lista fechada, nunca "todo elemento interativo"):** botão primário ("Publicar fluxo", "Salvar rascunho"), borda/anel do nó selecionado ou em hover, seta de conexão ativa/hover, sublinhado de aba ativa no painel, indicador de campo em edição (`.bl-painel-adicionar-tag:focus`), estado ativo do seletor de destino com busca (D-23). Nada além disso recebe verde de marca — rótulo, número, ícone decorativo e borda neutra continuam nos tokens de superfície/conteúdo/linha.

### Regra azul→verde e tokens semânticos por papel (D-30, D-32)

Toda cor azul da referência usada como marca/ênfase — incluindo hover, active, anel de foco visual, borda ativa, selecionado, highlight, glow, sombra, borda ativa, overlay e gradiente — vira o verde do Pipe. **Não existe um único verde substituindo tudo**: cada papel visual ganha seu próprio token semântico, para não achatar estados distintos na mesma cor (regra explícita do dono, ver `<specifics>` do CONTEXT.md).

Mecanismo (prescritivo, para o executor seguir sem reabrir a decisão):

1. Namespace novo em `packages/ui/src/estilos/tokens.css`, só dentro do escopo escuro (o Builder nunca lê o claro): `--p-builder-marca-*`. Não reaproveitar `--p-foco` (violeta) — esse token tem papel único e reservado a foco de teclado em todo o resto do produto; o "anel" visual do Blip no canvas é ênfase de marca, não foco de acessibilidade, e por isso usa um token de marca próprio, não o `--p-foco`.
2. Tokens a criar (valor inicial semeado de `--p-marca` escuro `#a3b76a`; cada um recebe seu valor final medido da referência durante a investigação/implementação, sem trocar o nome depois):
   - `--p-builder-marca` — cor base de marca dentro do Builder
   - `--p-builder-marca-hover`
   - `--p-builder-marca-ativo` — pressionado/active
   - `--p-builder-marca-anel` — o `box-shadow: 0 0 0 4px` de seleção/hover do nó
   - `--p-builder-marca-borda-ativa`
   - `--p-builder-marca-selecionado` — fundo/sublinhado de item selecionado (aba, item de lista)
   - `--p-builder-marca-destaque` — equivalente ao `color-mix(in srgb, var(--p-marca) 24%, #282828)` hoje hardcoded em `editor.css`
   - `--p-builder-marca-brilho` — glow/blur
   - `--p-builder-marca-sombra` — sombra tingida de marca
   - `--p-builder-marca-sobreposicao` — overlay/backdrop com tinta de marca
   - `--p-builder-marca-gradiente` — se algum gradiente existir na referência (a confirmar na investigação)
3. Espelhar em `packages/ui/src/tema.ts` como `TEMA.builder.marca.{hover,ativo,anel,bordaAtiva,selecionado,destaque,brilho,sombra,sobreposicao,gradiente}`, apontando para as custom properties (mesmo padrão já usado por `TEMA.marca`).
4. Documentar cada token novo em `docs/marca/MARCA.md` (valor, papel, onde é permitido usar) — exigência explícita de D-32.
5. Remover gradualmente `#4a5d23` (fallback hardcoded em `editor.css`, ~18 ocorrências) e `--bl-verde` (`painel-bloco.css:10`, 4 usos) conforme cada papel migra para o token semântico correspondente da lista acima. Não apagar antes de todo uso ter um token equivalente — `grep -rn "#4a5d23\|--bl-verde" apps/gestao-vite/src/paginas/builder` deve voltar vazio ao final da fase.
6. Preservar contraste, opacidade, blur e demais propriedades do efeito original ao trocar o hex pelo token (D-32) — a troca é de matiz (azul→verde), não de intensidade.

**Valor exato por papel:** pendente da investigação da referência (D-01/D-02). Este contrato fixa o *mecanismo* (nomenclatura, escopo, papel) para que planner/executor não hardcodem hex novo; o valor final de cada token é preenchido quando a tela correspondente é capturada no snapshot congelado ou herda o valor semente `#a3b76a` até lá.

## Copywriting Contract

Texto visível ao usuário continua em português (regra permanente, não afetada pela padronização técnica da Phase 1). Onde o conteúdo exato depende de uma tela ainda não investigada (D-01), o padrão abaixo é o piso/convenção de voz a seguir — não o texto final, que vem do snapshot congelado quando a tela existir na referência.

| Element | Copy |
|---------|------|
| Primary CTA (publicar fluxo) | "Publicar fluxo" (já existe, `painel-configuracao.tsx`) — mantém |
| Primary CTA (salvar rascunho) | "Salvar rascunho" — mantém convenção verbo + objeto já usada no Builder |
| Primary CTA (exportar versão antiga — D-16) | "Exportar versão" sobre a versão selecionada na lista de `GET :id/builder/versoes`; texto exato de cada estado da lista confirma com a referência antes de fechar (D-16) |
| Primary CTA (seletor de destino com busca — D-23) | placeholder "Buscar bloco de destino…", mesmo padrão de `painel-variaveis.tsx` |
| Empty state heading (canvas sem blocos / fluxo novo) | "Comece pelo primeiro bloco" |
| Empty state body | "Arraste um bloco da barra lateral ou clique em Novo bloco para começar o fluxo." — ajustar assim que a tela de Teste/Filas embutidas definir se têm empty state próprio |
| Empty state (painel de Teste, se confirmado como simulação local — Owner Question 2 do RESEARCH) | Heading: "Nenhuma execução ainda" / Body: "Envie uma mensagem de teste para simular o flufo a partir do bloco inicial." (texto final pendente D-14) |
| Error state (publicação inválida) | Já existe: 409 com `detalhe.erros` (`gestao-builder.ts`) — manter padrão "Não foi possível publicar: {motivo}. Corrija e tente novamente." |
| Error state (dependência externa não reproduzível, D-20) | "Esta ação depende de um serviço da Blip que o Pipe ainda não reproduz. Marcada como não executada — revise antes de publicar." |
| Destructive confirmation (excluir bloco) | "Excluir bloco: esta ação remove o bloco e desfaz as ligações que apontam para ele. Você pode desfazer com Ctrl+Z até sair da tela." |
| Destructive confirmation (excluir ligação) | "Excluir ligação: a seta some do canvas; o bloco de destino continua existindo." |
| Destructive confirmation (restaurar versão antiga) | "Restaurar versão: o rascunho atual é substituído pela versão selecionada. Publique de novo para valer no atendimento." |
| Destructive confirmation (limite de 15 no colar, já implementado) | Manter mensagem existente de `modelo.ts:342-388` — só confirmar paridade visual do toast/aviso, sem reescrever (D-17) |
